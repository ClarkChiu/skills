# translate 技能設計

> 2026-07-02。參考自製自 `JimLiu/baoyu-skills` 的 baoyu-translate（MIT；評估見 `research/audits/2026-07-02-baoyu-skills.md`）。方法取其「批評只診斷、修訂分離」的核心，工程與偏好系統全部不帶。已在對話中確認：方向雙向、方案 A（純文字零腳本）、兩模式。

## 1. 目標與範圍

**目標**：一個 EN↔zh-TW 雙向翻譯技能，核心是三段式紀律——初翻→自我批評（只診斷不動筆）→依批評重翻——讓譯文讀起來像目標語言原生寫成，而不是「翻出來的」。

**範圍內**：
- 方向：EN→zh-TW 與 zh-TW→EN，同一套流程、方向專屬的批評檢查清單。
- 模式：**快翻**（直翻，不留中間檔）與**精翻**（分析→初稿→批評→重翻，中間檔全留）。快翻後可說「繼續精翻」升級，沿用既有產出當初稿。
- 輸入：對話貼文、`.md`／`.txt` 檔案。
- 詞彙表：接既有 `chinese-typography` 的用詞層（見 §4）。

**非目標**（明確不做）：
- 不做上游的普通模式、EXTEND.md 偏好系統、分塊腳本、子代理平行翻塊、圖片語言檢查、網址抓取（要翻網頁先自行取回文字）。
- 不做 EN↔zh-TW 以外的語言對。
- 不自動呼叫下游技能（humanizer／chinese-typography），只在完成時建議（見 §6）。
- 不翻譯程式碼、識別字、專有名詞、JSON 欄位——維持原樣（與 CLAUDE.md 撰寫語言慣例的例外一致）。

## 2. 模式與觸發

| 模式 | 步驟 | 產出 | 何時用 |
|---|---|---|---|
| 快翻 | 直翻（套翻譯原則＋詞彙表） | 對話內直接給；來源是檔案才寫檔 | 短文、隨手翻、非發表用 |
| 精翻 | 分析→初稿→批評→重翻 | 四個中間檔＋最終檔（§5） | 要發表、重要文件 |

- 觸發詞：「快翻」「隨手翻」→快翻；「精翻」「要發表」「出版品質」→精翻；只說「翻譯」→**預設快翻**，但若輸入是整份檔案或超過約 800 字，提示「這份篇幅較長／要發表的話建議精翻」再繼續。
- 升級：快翻完成後固定提示可「繼續精翻」；升級時把快翻結果當 `02-draft.md`，直接從批評步開始。

**MUST**：精翻的批評步驟只產出診斷（問題清單），MUST NOT 在同一步改寫譯文——這是本技能的承重規則，防止「邊看邊改」讓批評流於表面。

## 3. 翻譯原則（兩模式共用）

沿用上游經驗，改寫為自己的表述：

1. **重寫而非直譯**：品質測試是「這段讀起來像不像目標語言原生寫的？」
2. **事實優先**：數字、日期、專有名詞、邏輯 MUST 與原文一致；不確定的術語標註原文。
3. **自然語序**：長句拆短、比喻按意圖轉譯不逐字。
4. **術語一致**：專業術語首次出現以括號附原文；全文用同一譯法。
5. **格式保留**：markdown 結構（標題、連結、程式碼區塊、圖片）原樣保留；程式碼區塊內容不翻。
6. **註釋節制**：只在目標讀者真的缺脈絡時加簡短說明，預設讀者是技術背景。

## 4. 詞彙表接線（zh-TW 方向的權威順序）

譯入 zh-TW 時，用詞依此優先序，高層凌駕低層：

1. `chinese-typography/user-dictionary.json` 的 `replacements`（機械強制層，如 訊令→信令）
2. `chinese-typography/references/glossary.md`（個人用詞釘選＋但書）
3. 本技能自帶 `references/terms-en-zhtw.md`（EN↔zh-TW 術語對照，聚焦使用者領域：網路／協定／測試自動化／雲端；雙向共用一張表）
4. 臺灣一般出版慣例（OpenCC s2twp 詞彙取向）

譯出 EN 時只用第 3 層反查（中→英術語）。**MUST NOT** 在 SKILL.md 裡複製 glossary 內容——只寫「讀這兩個檔」，避免兩處真相。

## 5. 精翻流程與中間檔

輸出目錄：來源檔旁 `<basename>-<方向>/`（如 `report-zhtw/`）；對話貼文則所有中間檔寫進系統暫存區、最終譯文貼回對話。

| 檔 | 內容 |
|---|---|
| `01-analysis.md` | 內容摘要、術語表（含從全文抽出的新詞）、語氣評估、翻譯難點（比喻／雙關／長句） |
| `02-draft.md` | 初稿（套 §3 原則＋§4 詞彙表） |
| `03-critique.md` | **只診斷**：對照原文逐段檢查，依方向專屬清單列問題（位置＋描述＋建議修法），結尾統計 |
| `04-final.md`（或 `translation.md`） | 依批評逐項修正後的最終稿（上游的修訂＋潤色併為一步） |

長文處理（無腳本的天花板策略）：先通讀全文完成 `01-analysis.md`（術語表建在這步＝跨節一致性的保證），再按標題分節翻譯合併；節間銜接問題交給批評步驟兜底。`# 天花板：幾萬字級長文若出現節間不一致，屆時再評估加 Python 分塊腳本（方案 B）`。

## 6. 批評檢查清單（方向專屬，各一檔）

**EN→zh-TW**（`references/critique-en2zhtw.md`）：
- 準確性：事實／數字／專有名詞逐段對照；漏譯、增譯、改義。
- 翻譯腔：歐化句（「進行了…」「…性」名詞化）、被動濫用（被／由／受到）、連接詞堆疊（因此／然而／此外）、代名詞冗餘、長定語。
- 臺灣用語：對照 §4 詞彙層；抓中國用語混入（軟件／視頻／信息…）。
- 排版預檢：盤古之白、全形標點的明顯缺失（正式修正交給下游 chinese-typography，這裡只抓大的）。

**zh-TW→EN**（`references/critique-zhtw2en.md`）：
- 準確性：同上。
- 中式英文：冠詞缺漏、時態單一、主詞懸空、逐字直譯的搭配錯誤（如 open the light）、句子全是簡單句串接。
- 語域：technical writing 的簡潔慣例（主動語態、動詞優先、砍冗詞）；標題大小寫一致。

與 `humanizer` 的邊界：humanizer 抓「AI 生成腔」（灌水、三段式、AI 詞彙），本清單抓「翻譯腔」（源語言結構殘留）——兩者相鄰不重複，各自維護；批評清單 MUST NOT 複製 humanizer 規則，發表前要去 AI 味就建議接著跑 humanizer。

完成時的下游建議（不自動執行）：譯入 zh-TW → 建議跑 `chinese-typography` 正規化（純中文文字，安全）；要發表 → 再過 `humanizer`。

## 8. 驗收準則（Given/When/Then）

1. Given 一段含「signaling」的英文技術段落，When 快翻成 zh-TW，Then 譯文用「信令」且首次出現附原文括號。
2. Given 使用者說「精翻這份檔案」，When 流程跑完，Then 輸出目錄存在 `01-analysis.md`～`04-final.md` 四檔，且 `03-critique.md` 只含問題清單、不含改寫後全文。
3. Given 一段被動語態密集的英文，When 精翻，Then `03-critique.md` 至少點名被動濫用處，且 `04-final.md` 對應句改為主動或自然句式。
4. Given 一段 zh-TW 段落要譯英，When 精翻，Then 批評步用 zh-TW→EN 清單（查冠詞／時態），不誤用中譯方向清單。
5. Given 快翻剛完成，When 使用者說「繼續精翻」，Then 不重翻初稿，直接以快翻結果進批評步。
6. Given 原文含程式碼區塊，When 任一模式翻譯，Then 程式碼區塊內容逐位元不變。

## 9. 風險與自我審查

- **範圍蔓延風險**：上游功能多，實作時容易「順手加回」EXTEND.md 或分塊——非目標清單（§1）是硬邊界。
- **清單與 humanizer 重複風險**：§6 已畫界（翻譯腔 vs AI 腔）；evals 加一條確認批評清單不含 AI 詞彙類規則。
- **佔位符**：本文件無 TODO／佔位符；模式、方向、詞彙層、檔案佈局皆已具體。
- **一致性**：§2 預設快翻＋長文提示，與 §5 長文策略相容；§4 權威順序與 glossary.md 自述的三層分工一致。
